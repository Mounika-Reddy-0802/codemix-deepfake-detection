# Problems & decisions (ADR log)

Numbered decisions and the problems that motivated them, versioned alongside the
code. Newest entries can be appended; existing ones are not rewritten.

| ID | Decision | Why |
|----|----------|-----|
| **P-001** | Stage-1 trains on **ASVspoof 2019 LA (English) only** | The English → Hindi/Tamil → code-mixed gap is only a *measurement of generalisation* if nothing else leaks into training. Enforced by `tests/test_splits.py`. |
| **P-002** | **HiACC child audio excluded entirely** — never bonafide, never a cloning reference, never in a manifest | Ethics. Quarantined into `_EXCLUDED_children/` on extraction; checked in `build_manifests` + `select_reference_speakers` + `test_splits`. |
| **P-003** | **Tortoise held-out tool lives in `heldout_tts.py`**, separate from `spoof_generation.py` | Keeps the unseen-attack tool firewalled *and* lets L (scale) and SK (held-out) edit different files in the same week without merge conflicts. |
| **P-004** | **Heavy imports are lazy** (torch/transformers/TTS/torchaudio/librosa/silero inside functions) | CI installs only ruff/pytest/numpy/pandas/pyyaml and stays fast + green; modules still import for pure-logic unit tests. |
| **P-005** | **Metrics in pure numpy** (custom EER, rank AUC, F1, bootstrap CI) — no sklearn | Removes a CI dependency; results are exact and unit-tested against known cases. |
| **P-006** | **G.711 μ-law + SNR mixing in pure numpy**; AMR-NB via ffmpeg with G.711 fallback | The lossy pieces that matter for the paper are exact + testable; AMR-NB stays optional so the pipeline runs without ffmpeg. |
| **P-007** | **One branch per person per week** (`week<N>/<firstname>`), merged into `main` after the week | Individual contribution is graded from git history; merging keeps `main` complete so the next week branches off a full tree. |
| **P-008** | **Pushes run in the background** | Pushing from the OneDrive-synced working copy is slow (sync contends on `.git` pack files); a foreground push can exceed a 5-min timeout while the same push completes in the background. |
| **P-009** | **Twilio activated in Week 6, not before** | The 30-day trial window is timed to cover Weeks 6–9 (integration + demo). Weeks 1–5 use the free WebRTC harness. |
| **P-010** | **Pilot transcripts are capped at 150 characters, the tightest XTTS limit across the pilot's language tags** | XTTS-v2 truncates silently past a per-language limit (hi 150, en 250) and only warns on stderr. Choosing transcripts longest-first put **19 of 20** jobs over it (median 278 chars), so raters would have scored truncation instead of code-switch quality. The cap is the *minimum* across tags, not per-tag, so `latn_en` and `latn_hi` differ only in the tag — a per-tag cap would have given the en cell 250-char utterances and confounded length with language. |
| **P-011** | **Hindi transcripts containing digits are excluded from generation** | XTTS's `hi` cleaner calls `num2words(n, lang="hi")`, which is unimplemented and raises. MUCS is NPTEL lecture speech, so numbers are common — this killed a pilot run at clip 7. Filtered at job assembly (`is_synthesisable`) and survivable at run time (see P-012). Revisit for Week 4: pre-expanding numerals into Devanagari words would recover this material instead of dropping it. |
| **P-012** | **`generate_batch` continues past a failed clip and logs it to `generation_failures.jsonl`** | A 4,000-clip Week-4 run must not die on one unsayable transcript. Failures are recorded rather than swallowed: the datasheet has to state how many transcripts the generator could not say, and why. |
| **P-013** | **`channel_qa` aligns on codec delay before measuring SNR and correlation** | AMR-NB delays output ~4.8 ms (76–80 samples at 16 kHz); G.711 does not. Measured at offset 0, that shift read as correlation ≈ 0 and negative SNR, failing 15 of 20 pairs on a chain that was working. Alignment is bounded to ±100 ms and never rescues genuinely unrelated audio (tested). |
| **P-014** | **The corpus is written in ONE script, and it is Latin.** Devanagari is transliterated to romanised Hinglish (`src/data/transliteration.py`) before text reaches XTTS; the source text is kept in a `transcript_source` column | Team decision, 17 Aug 2026. No team member reads Devanagari, and a rater who cannot read the target sentence can only judge whether a clip *sounds* pleasant — not whether it said the right words, which is what the pilot exists to measure. Filtering could not deliver a Latin-only corpus: MUCS is **98.2% Devanagari-bearing** (only 957 of 52,825 transcripts contain none, and those are plain English, not Hinglish), and just **17** usable Devanagari-free transcripts exist inside the frozen 25-speaker train pool. So the Latin text has to be *produced*, not selected. Hand-rolled rather than a library because CI installs only ruff/pytest/numpy/pandas/pyyaml (P-004), and because the spelling is an *input to XTTS* that must stay frozen — a library upgrade changing one vowel would generate half the corpus from a different romanisation, invisibly. |
| **P-015** | **The romanised length, not the Devanagari length, is what the XTTS character limit is applied to** | Romanisation inflates text ~13% on average and up to 58%. Measured on this corpus, **14 of the 20** pilot transcripts cross the 150-character Hindi limit once transliterated. Filtering on the source length would hand XTTS text it silently truncates — precisely the P-010 failure, re-entering through the back door. `spoken_text()` is the single definition of "what the model receives" so the filters and the job table cannot disagree. Cell membership still keys off the **source** script: after transliteration every transcript is Latin, so classifying the output would collapse all four cells into one. |
| **P-016** | **Reference and transcript selection break ties on `utt_id`, not on index row order** | MUCS segment durations are whole seconds, so ties are the rule, not the exception. With `duration_seconds` as the only sort key the winner fell out of `clip_index.csv` row order, which follows the filesystem walk — so the CPU laptop and the GPU laptop built the *same* pilot with speakers 4 and 5 swapped in every cell (177570 and 850754, both exactly 20.0 s). `deva_hi_04` was therefore a different person on each machine, and a rating sheet keyed on position would have mis-attributed every score. `utt_id` is unique across all 56,143 rows, so it settles every tie identically anywhere. Pinned by `test_the_whole_job_table_is_reproducible_across_index_orderings`. |
| **P-017** | **The RVC pilot (W3-T5) is BLOCKED on toolchain, not on GPU or ethics.** RVC is deferred to W4-T2, and the second attack family must not be assumed available until a working install exists | `rvc-python` pulls in `fairseq`, whose build requires an old numpy that calls `pkgutil.ImpImporter` — **removed in Python 3.12**. `pip install rvc-python` therefore fails at "Failed to build 'numpy'" before anything is downloaded. This laptop has only Python 3.12.7 and no conda, so there is no interpreter to fall back to. Three ways out, none free: install Python 3.10 alongside and give RVC its own venv (fairseq's last working line); use a fairseq-free RVC fork (re-validates the whole conversion path); or drop RVC and keep Tortoise as the only second family (weakens the "two attack families" claim in the v2 scope the mentor signed). **Do not attempt the install in the project venv** — the resolver downgrades torch and would break the XTTS stack that currently generates. Recorded as the *RVC viability* answer W3-T5 asks for: viable in principle, not installable here today. |
| **P-018** | **RVC is UNBLOCKED on Windows. P-017's diagnosis was wrong**: the wall was never Python 3.12, it was four separate walls, and `fairseq` now compiles. RVC runs from its own Python 3.10 venv at `C:\dfdata\rvc_env`, isolated from the project venv | P-017 read the first error (`fairseq` → old numpy → `pkgutil.ImpImporter`, removed in 3.12) as *the* blocker. On Python 3.10 the real chain turned out to be: (1) every `rvc-python` release pins `omegaconf==2.0.6`, whose 2021 wheel declares `PyYAML (>=5.1.*)` — malformed, and **pip ≥ 24.1 refuses it**; pinning pip to 24.0 *inside that venv* clears it. (2) `fairseq` 0.12.2 has **no wheel for any current Python**, so it must compile. (3) `winget install Microsoft.VisualStudio.2022.BuildTools` laid down a partial MSVC with **no Windows SDK and no Hostx64 `cl.exe`**, so the compile still failed with the same "Visual C++ 14.0 required" message. (4) `vs_installer modify --add VCTools --add Windows11SDK` fixed it and **exited 87 while actually succeeding** — the toolchain has to be checked on disk, not inferred from the exit code. Result: `fairseq 0.12.2` builds, `rvc_python.infer.RVCInference` imports. The venv is deliberately separate: `rvc-python` drags in `torch 2.13.0` and `numpy 1.23.5`, either of which would break the XTTS stack that currently generates. |
| **P-019** | **XTTS-v2 compresses pitch range by ~35% and no generation parameter fixes it.** Recorded as a measured property of the seen-attack family, not a tuning bug | The pilot clips read as obviously cloned. Measured against real speech: median intra-utterance pitch range (f0 IQR) is **42.2 Hz** for spontaneous HiACC and **41.1 Hz** for the MUCS lecture speech we clone from, but only **25–29 Hz** for every XTTS configuration tried — single longest reference (27.1), most-expressive reference (29.0), temperature 0.95 (24.2, *worse*), expressive + hot (25.4), and five reference clips totalling 49–115 s (26.9). XTTS invents prosody from text and regresses to a flat contour; the reference supplies timbre, not intonation. Two related mismatches: pause fraction 0.21 (HiACC, spontaneous) vs 0.38–0.40 (MUCS lecture and our clips), and median pitch 187 Hz (HiACC, 14M/10F) vs 110 Hz (our MUCS train pool, gender metadata absent). **Consequence for the paper:** the XTTS family is a legitimate but *easy* attack, so detector numbers against it are optimistic and the f0-IQR gap belongs in the datasheet. This is the reason the plan pairs XTTS with RVC (P-018): voice conversion starts from real speech, so the pitch contour is human and this compression cannot occur. |
| **P-020** | **Upstream RVC-WebUI was restructured, and P-017/P-018's `fairseq`/MSVC diagnosis no longer describes it: there is nothing left to compile.** The CM02 run is driven from the upstream checkout's own scripts with three fixes recorded below, and `requirments_*.txt` is deliberately not installed | Three things changed upstream since P-018 was written: `fairseq` is gone entirely, HuBERT is a **Transformers model directory** (`assets/hubert_base/{config.json, preprocessor_config.json, pytorch_model.bin}`) rather than the fairseq `hubert_base.pt`, and the training scripts moved from `infer/modules/train/` to `train/`. So the `omegaconf` / `pip<24.1` dance, the MSVC Build Tools saga and the Python 3.10 venv in P-017/P-018 are all obsolete — on Linux the toolchain is four pip packages (`av`, `ffmpeg-python`, `praat-parselmouth`, `faiss-cpu`) on top of the stock Kaggle image. Downloading a single `.pt` to the old HuBERT path is the failure that looks like it worked and then raises `FileNotFoundError` during feature extraction. **Three defects had to be fixed before the first target trained.** (1) The Kaggle upload of MUCS preserves `mucs2021/...` but not the `raw/` anchor that `src.utils.paths.resolve()` rebases on, and `/kaggle/input` is read-only, so the notebook links the corpus under a `raw/` anchor in `/kaggle/working` instead of requiring a re-upload. (2) `clip_index.csv` is gitignored (machine-local absolute paths), so a fresh clone never has it and step 4 died on a missing file; it is now rebuilt from MUCS's own Kaldi tables (52825 rows, 520 speakers). (3) RVC's stage scripts live in subpackages but import each other as top-level packages, and `python train/preprocess.py` puts the *script's* directory first on `sys.path` — so the checkout root is absent (`No module named 'infer'`) **and** `train/train.py` shadows the `train` package (`circular import of a partially initialised 'train'`). Both surface only after the training wavs have been staged. Fixed in `rvc_generation._stage_env` with `PYTHONPATH=<checkout>` plus `PYTHONSAFEPATH=1`, pinned by `tests/test_rvc_generation.py`, and preflighted in the notebook so a broken path costs two seconds rather than a staging pass. |
| **P-021** | **P-019's “XTTS-v2 compresses pitch range by ~35%” does not survive re-measurement: the error is in its *real-speech baseline*, not its XTTS figure.** On one consistent estimator XTTS-v2 is ~27% **wider** than the speech it clones, not 35% narrower. The CM02 prediction is unaffected and still holds | P-019 reported median intra-utterance f0 IQR of **41.1 Hz** for MUCS against **25–29 Hz** for XTTS-v2, measured ad hoc with no committed code. W4-T2 shipped `src.data.f0_stats` (Praat autocorrelation, 60–400 Hz) and measured the CM02 run with it: real MUCS source **21.8 Hz**, RVC converted **21.1 Hz** (96.4% retention, one pass, one estimator). Re-running that same call over the W3-T5 XTTS pilot clips returns **27.8 Hz** (23/25 usable) — which **reproduces P-019's XTTS number exactly**, while the same tool puts real MUCS at 21.8 Hz rather than 41.1 Hz. So the two figures P-019 compared came from different methods and the 35% compression is an artefact of that comparison; XTTS does not flatten prosody, it overshoots it. **What survives:** CM02 remains a distinct attack family, on a cleaner argument — the two generators deviate from real speech in *opposite* directions (RVC tracks it, XTTS overshoots), so pitch range still separates them and a detector trained only on CM01 has not seen CM02's behaviour. **What is still open:** the XTTS row is 23 pilot clips against 1493 for the others. It is enough to retire the 41.1 Hz baseline, not enough to be the paper's number — re-measure the ~4,000 CM01 scale clips with the same call once they are recovered. P-019 is left in place unedited; this log is append-only and the correction belongs beside it, not over it. |
| **P-022** | **The shortcut gate asked of CM02 fails at 22.3% EER — 16× further from a shortcut than CM01's 1.39%, and for a different reason: RVC's tell is spectral, not level.** Normalisation, which moved the CM01 gate 3.7×, buys 0.14 pp here | CM02 can be asked a stricter question than CM01 because every RVC job records the source segment it converted, so the gate compares 1,500 conversions against the **1,345 source recordings they were made from** — same words, same room, same microphone, fit/score disjoint by source speaker (13/12 of 25). Anything it finds is the conversion and nothing else. Result: **22.42% EER raw, 22.28% normalised** (chance 50%; CI [20.0, 24.9] and [19.7, 24.4]; 1,369 scored clips, 0 missing). Both are FAIL against the plan's near-chance band, and both are far better than CM01's 1.39% / 5.17%. **The mechanism is the interesting part.** Level normalisation does exactly what it should — RMS mean and std equalise to within 1% — and the gate does not move, because the separation was never in the levels: it is carried by `zero_crossing_rate` (0.1324 source vs 0.0798 converted, 40% lower, top coefficient in both conditions at +2.648 / +2.719) and `hf_energy_ratio` (0.0047 vs 0.0023, half), which are scale-invariant. RVC's decoder reconstructs from pitch and content features and does not reproduce the source's high-frequency detail — room noise, breath, fricative energy. It keeps the prosody (P-021: 96.4% f0-IQR retention) and loses the top of the spectrum. **Consequence:** this is P-021's "opposite directions" argument arriving from a second direction — CM01 and CM02 are separable from real speech by *different* cheap statistics, so a detector trained only on CM01 has not seen CM02's behaviour. It does **not** clear the clean 1.34%, which is measured on the XTTS bundle this gate does not touch. It does mean a CM02 model number has a 22.3% shortcut baseline to beat rather than a 1.39% one. The raw condition's #2 and #3 features (`dc_offset` −0.0022 vs 0.0000, `clipping_ratio` 0.0001 vs 0.0000) are near-degenerate artefacts of writing clean zero-mean float audio, not properties of conversion; they vanish under normalisation, which makes the normalised run the more honest of the two. **Next:** run the gate on the channel-matched condition — band-limiting moved CM01 from 1.39% to 9.25% by destroying HF evidence, and CM02's tell *is* HF, so it should compress harder. |
